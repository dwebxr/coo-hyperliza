# What the Agent Downloads

A world tells its clients what to download: models, avatars, emotes, scripts, the sky. A builder can ask Coo to import a file from a URL, a sandboxed script can call `fetch()`, and another plugin can hand Coo an audio URL to transcribe. All of these go through one policy (`src/plugin-hyperfy/lib/net-policy.ts`):

- **Public `https://` hosts on the default port.** A host name is judged by the addresses it resolves to, at the moment the connection is made, and the connection goes to the address that was checked. Loopback, private, link-local, carrier-grade NAT, multicast and cloud-metadata addresses are refused, in every spelling (`https://2130706433/`, IPv4-mapped IPv6, NAT64, 6to4 ...), and so is a name with even one such address among several. No user name or password in the URL.
- **The world's own origin**, whatever its address, port and scheme: the origin of `WS_URL` (`wss://` becomes `https://`, `ws://` becomes `http://`). That is what keeps a local or LAN world working. It is that origin only, with one allowance for a world on loopback: when `WS_URL`'s host is `localhost`, `127.x.x.x` or `[::1]`, the same scheme and port on any of those spellings count as the world too (`ws://127.0.0.1:3000/ws` covers `http://localhost:3000`, and the other way round). Nothing wider: another port, another scheme, or another name for the same machine (a LAN name, `me.localhost`, `[::ffff:127.0.0.1]`) is another origin. A world that names its assets under another origin gets them loaded only if that origin is a public `https://` host (a bucket or CDN is fine); otherwise the agent logs which URL it will not use and why when it joins (for an `https://` name that only turns out to resolve to a non-public address, the refusal appears with each failed download instead), and the fix is to write `WS_URL` with the host name the world itself uses.
- Redirects are followed by hand, at most five, and each one is judged from scratch: a redirect off the world's origin loses the exception.
- One deadline per download (60 seconds for a model, avatar or import, 30 for an emote, image, HDR or audio, 15 for a script), and a size cap enforced while the bytes arrive: 50 MB for models and avatars (also for imports, where the world's own upload limit lowers it and can never raise it), 16 MB for emotes, 2 MB for scripts, 32 MB for images, HDR environments and audio (MB here and below is 1024 × 1024 bytes). An answer that is compressed although the agent asked for none (`Content-Encoding`) is refused. Per connection the loader runs at most 8 loads at once and lets 1,024 wait (more are refused); the engine's requests for images, video and audio are not downloaded at all.
- **Uploads** (the avatar, emotes, imported models) carry the agent's session token, so they go to the world's own origin only. The one function that attaches the token checks each request's own URL against that origin (and refuses a user name or password in it) before anything is sent, and an upload reads the world's API URL once: its check and its POST go to the URL that was checked, whatever the world announces meanwhile. A world whose API URL is on any other origin gets no upload: the agent logs that once when it joins, never sends the token there, and keeps the world's default avatar unless the world already serves the avatar file. A redirect from the upload API is not followed.
- Sky images and HDR environments are fetched one sky at a time: a newer sky stops the download of the one before it. Once a world is gone, nothing more is downloaded or handed to the render page for it. A page call already running then (decoding a texture, an avatar or an HDR) cannot be interrupted: the page keeps what the call kept on record until the agent settles it. The agent first does its own work on the result (for a model: parsing and converting it), then makes one last check: when the call or that work failed, or the world went away by then, all of it is taken back; otherwise the record is dropped and the result is the agent's (a sky texture that a newer sky replaced during that last step is then released). A settlement that fails fails the load, and the page holds no record of a call beyond its settlement. A model whose materials carry a `materialId` the page cannot use as one fails to load, and what the load had kept in the page goes with it.
- Log lines and error messages write the URL of a download, an import or an upload as scheme, host and path only: no user name or password, no query values (their names stay; a query part without `=` counts as a name and is written), no fragment, at most 200 characters in all, a note of the full length included (`src/plugin-hyperfy/lib/log-url.ts`). The lines logged on joining about the world's own API and assets URLs name their origin instead, uncut (and an assets URL that is not a URL at all as it came).
- The listings request of the OpenPay Store shop goes through the same policy, so `OPENPAY_STORE_API_URL` must be a public `https://` URL.

## What Bounds the Render Page

Source: `src/plugin-hyperfy/lib/render-watchdog.ts`.

Each Chromium the agent launches runs in its own process group. For as long as it exists, the resident memory of everything it owns (its process tree, its process group, and every process seen in either, for as long as that process stays in the group it had) is sampled again 2 seconds after the previous sample finished, and 250 ms after it while the agent has the page working on something (loading a model, avatar, image or HDR, taking a snapshot), so the time `ps` itself takes (at most 5 seconds) adds to the gap. When that goes over 3 GiB, or a page call takes longer than 60 seconds (building the page, 30), that browser is torn down at once: every call in flight fails, any later call to it fails too (without being blamed for the kill), and its processes are killed by group and by pid; the next use launches a new one. For this machine's bundled assets the tree measured 0.85 to 0.86 GiB idle and at most 1.63 GiB, and the slowest call took under 0.5 s. A model, image or HDR whose page call was the only one in flight when Chromium was killed is not handed to the page again on that connection (said once in the log; at most 256 such URLs are kept per connection, and a reconnect starts with none), and from the first kill on that connection's page loads run one at a time, so that the next kill has one load to blame (a snapshot or a page build in flight at the same moment still means nobody is blamed). Whatever the URLs and whichever world caused them, 3 kills within 10 minutes open a circuit breaker for the whole process: for the next 10 minutes every page call fails at once (`RenderPageUnavailable`), also one that was waiting for a browser launch or a page build when it opened (checked again once that completes, before any page work), logged when it opens and when it closes. When `ps` cannot be read, only the deadlines apply: that is logged once, sampling retries with a growing pause (at most 30 seconds), and the agent logs once when it can read it again. The page itself keeps at most 1,024 textures and 32 avatars, dropping the least recently used. The browser launch is bounded by puppeteer's own launch timeout, not by this. What this cannot do: memory can go over the limit by what the page allocates between two samples; a kill drops everything the page held (textures, avatars, the environment) until the next connection brings it again; resident size is counted per process (shared pages in each); a process that leaves Chromium's group and tree before it is ever sampled is not seen.

## The Model and Emote Filter

What is refused before a model reaches the page, or an emote the agent's own parser (`src/plugin-hyperfy/lib/gltf-budget.ts`): a filter for the amplifiers that are cheap to put in a file, not the limit above. The container is read the way the page's loader reads it (version 2, a declared length equal to the file's, chunks within bounds and multiples of 4 bytes, one JSON chunk first, at most one BIN chunk, nothing else); the JSON may nest at most 64 deep and be at most 16 MiB in UTF-8 without its `data:` URIs (both checked before it is parsed); it must declare `asset.version` 2.x, name only things that exist (the textures its materials name, and the images and samplers of those textures, included), keep buffer views inside their buffers and accessors, sparse parts included, inside their views, and have a node tree that is a tree. Refused on purpose, though valid glTF: Draco, triangle strips and fans, legacy `animation.parameters`, animation data in interleaved views, primitives that the loader would give one geometry but that declare different morph targets (compared by content), and a required extension the page cannot decode (meshopt, BasisU, anything it does not know). Checked against the 23 models bundled with the agent (an avatar exported by UniGLTF with 32 sparse accessors among them) and 25 assets of the owner's worlds (Blender 4.4 exports that require `EXT_texture_webp`, a Blender VRM export), which all pass; how often other exporters write what is refused is not known. The simple allocations are charged (copies of the BIN chunk and of every buffer view, every accessor, decoded `data:` buffers, embedded images per sampler, animation data converted to floats, morph targets and skin matrices as the export writes them): one at most the download cap (50 MB; 16 MB for an emote), all at most eight times the cap; the export they add up to must fit four times the cap (the next section lowers what the page may actually hand back). Counts are capped too (every top-level collection, cameras and lights included; the mesh instances the scenes expand to; the animation tracks generated; extras and extension data times the copies made of them). Not covered by the filter, and left to the watchdog: image decoding (a small image can declare huge dimensions), what the VRM plugin builds from its own extensions, and the re-encoding of textures that stay on an exported avatar.

## What Bounds the Agent's Own Memory for Assets

Source: `src/plugin-hyperfy/lib/asset-memory.ts`.

Before the loader or the sky downloads a world asset, it reserves memory in this process from two pools of 1 GiB in all. Downloads, 256 MiB: twice the kind's size cap (the chunks and the one copy they are joined into), cut to twice the `Content-Length` when the answer declares less, and to twice the actual size once the bytes are in. Then the rest of the way, 768 MiB, exchanged for the download once: what is sent to the page costs 6 times its bytes (the bytes and three copies of their base64: the string, the message, the frame), what comes back 7 times (three copies of its base64, the decoded copy, the engine's copies of its BIN chunk and buffer views), a script 3 times. For a model or avatar what comes back is not estimated: the agent reserves for the most the page may return for this load and tells the page that number, which it refuses to go over. An emote does not go to the page: it is parsed in the agent, and reserves its download plus what the filter charged for it. That ceiling is twice the filter's export estimate or the download times 2 (8 for an avatar, which keeps its textures in the export), at least 1 MiB, at most the kind's export budget, and lowered until 6 × download + 7 × ceiling fits the pool: a 50 MB model may get back at most about 67 MB, and a model whose estimated export does not fit is refused. After the exchange a reservation only shrinks; it is given back when the load ends, whether it worked or not. Small files still load side by side (the bundled avatar reserves about 150 MiB, the base environment about 28 MiB), larger ones wait their turn, first come first served, and a load waiting for memory stops when its world goes away. So the copies listed here stay within 1 GiB. Not counted: the three.js objects and scene graph the engine builds from a parsed model; the cache of finished loads, which has its own bound (512 MiB and 256 entries, each model counted at the larger of its download and the copy the page handed back); and what does not go through the loader or the sky at all: a file a builder asks Coo to import (up to the 50 MB cap, with its upload copies), audio handed over by URL (32 MB), a script's `fetch()` answers (1 MB each) and the shop's listings (4 MB).

## What This Does Not Do

- It trusts the world's own origin completely. Anything that can name a URL (the world, a script, an import request) can make the agent `GET` any path on that origin, without credentials. Do not point `WS_URL` at a host that also serves something private.
- The agent can be made to fetch from any public `https://` host, which shows that host the agent's address. Nothing here limits how often.
- These requests do not go through `HTTP_PROXY`/`HTTPS_PROXY`. Where the only way out is a proxy, they fail (and the uploads with them), while Claude and ElevenLabs, which use the runtime's own `fetch`, keep working.
- The voice connection is covered only up to the URL. The world names a LiveKit server; the agent hands it to LiveKit's native client only when it is `ws://` or `wss://` with no user name or password, and either on the world's own host (any scheme and port; loopback spellings count as one host) or `wss://` on the default port of a host whose every address is public, judged as above. Otherwise voice stays off and the agent logs one line saying why. What is not covered: the native client resolves the host name again itself when it connects, so a name whose answer changes between the check and the connection is connected to at its new address, whatever that is; and the media connections the native client then makes (ICE, TURN, the addresses the LiveKit server hands it) are not checked at all.
- Requests the agent makes to fixed services (Claude, ElevenLabs, OpenAI speech) are not world-supplied URLs and are not part of this. The OpenAI voice on `gpt-realtime-2.1-mini` is one WebSocket to `wss://api.openai.com/v1/realtime` per utterance, opened only when it is to speak; unlike `fetch`, it does not go through `HTTP_PROXY`/`HTTPS_PROXY`, so where the only way out is a proxy the fallback fails and the reply goes to chat as text.

## The Offline Render Page

The headless Chromium the agent uses for its snapshots has no way to make a request or resolve a name (WebRTC/UDP is not blocked by these settings; nothing in the page uses it). Its page is bundled at build time (three.js 0.132.2 and three-vrm 3.3.3, the versions it was written against; nothing is fetched from a CDN any more; three-vrm 3.3.3 asks for three.js 0.137 or later: the page adds the two light functions its toon shader calls in their newer form, and drops the tangents of toon meshes, which that shader cannot read here, see `public/puppeteer/page.js` and `assets.js`; the colours of toon avatars are not converted the way three.js converts its own materials), the agent downloads every asset itself under the policy above and passes the bytes in, every request the page makes is refused, and the browser is started with a proxy address where nothing listens and no name resolution, so that the browser's own background requests go nowhere either. A model that refers to files outside itself (a `.gltf` with separate buffers or images) is not given them: it fails to load, or is drawn without them. Chromium and ffmpeg are started with a reduced environment: no API keys, no tokens, no database URL.

## Debug Snapshots

`HYPERFY_DEBUG_SNAPSHOTS=true` makes the agent write each snapshot it takes to its working directory (`scene_equirectangular.jpeg`, `scene_facing_<direction>.jpeg`, `scene_view_to_target.jpeg`). Without it, nothing is written. With it the agent also logs, for each snapshot, what it sent to the render page and what the page made of it, in numbers (`[PuppeteerManager] Snapshot scene sent: …` and `… in the page: …`: meshes, instances, lights, textures kept, triangles drawn, shader programs that failed), and passes on the errors and warnings of the page's own console (`[RenderPage] …`, each cut to one line and logged once, at most 40 different ones per page): that is where three.js reports a shader or a scene it cannot read.
